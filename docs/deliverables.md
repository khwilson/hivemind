# Hivemind deliverables and standard work

**Status:** product requirements for the GitHub-backed design. These deliverables
are intended behavior, not a claim that the current draft implements them.
Each project coordinates inside its target repository, as specified in the
[design](design.md). Round one uses GitHub for queue state and communication.

## Setup and agent CLI

Ship an installable uv-managed Python package with a Typer CLI. The same CLI
serves project maintainers and authorized agents, using different capabilities.

| Proposed command | Result |
| --- | --- |
| `hivemind init --repo OWNER/REPO --profile mathematics` | Prepare project configuration, broker workflow, instructions, skills, and standard-work rules |
| `hivemind setup --repo OWNER/REPO` | Apply authorized GitHub setup and report remaining manual App or permission steps |
| `hivemind doctor --repo OWNER/REPO` | Verify setup, branch rules, credential restrictions, registry, and workflow version |
| `hivemind upgrade --repo OWNER/REPO` | Propose a versioned installation update while preserving local instructions |
| `hivemind keygen`, `agent register`, `agent revoke` | Manage local signing keys and the protected project allowlist |
| `hivemind task add`, `edit`, `prioritize`, `show` | Use the same broker-validated queue operations as the viewer |
| `hivemind claim`, `heartbeat`, `release`, `submit` | Perform the fenced agent work loop |
| `hivemind hint`, `conversation watch` | Preserve repository findings and follow relevant GitHub threads |

Initialization produces concrete files and a readable change summary. Existing
repositories receive a setup PR for protected files; an empty repository can be
bootstrapped directly by its authorized maintainer. Setup is repeatable: rerunning
it must not duplicate workflows, marked instructions, keys, or standard tasks.
It must not silently replace human configuration or grant agents bypass access.

The CLI initializes the orphan state branch, configures the agreed rulesets and
restricted Actions environment where the caller has permission, and supplies
exact instructions for manual steps such as registering the broker App.
Credentials are accepted through secure local input or credential storage,
never committed or placed in CLI output. `doctor` reports incomplete setup rather
than declaring success after only writing files. Routine broker and viewer
updates deploy through GitHub Actions; no AWS setup is required in round one.

Agents receive JSON output with task revision, acceptance criteria, dependencies,
claim fencing ID, lease expiry, and request receipt. A pending request does not
confer ownership. The CLI distribution bundles the viewer assets and template
versions so an installation can be reproduced without depending on mutable
copies of prompts elsewhere.

## Repository instructions and skill bundle

Ship templates in the package and repository, then install selected templates
into the governed checkout. A root `AGENTS.md` provides the common workflow;
individual reusable skills use `SKILL.md` files, with optional supporting files.
Agent-runner-specific paths are adapters, not a requirement to use one runner.
A skill catalog lists the installed skills and how an agent should find them.

Proposed installed layout:

```text
AGENTS.md                         # existing rules plus marked Hivemind section
.hivemind/
  project.json                    # coordinating repo and project identity
  config.json                     # protected authorization and evidence policy
  standard-work.json              # protected rules for automatic follow-up work
  templates.json                  # installed versions and managed file hashes
  hints/<task-id>.md              # committed findings and handoffs
  skills/
    agent-work-loop/SKILL.md
    mathematics-review/SKILL.md
    mathematics-generalization/SKILL.md
    proof-and-evidence/SKILL.md
    handoff-and-followups/SKILL.md
```

The skills cover claiming and renewal, reading context, mathematics inspection,
proof evidence, communication, and creating useful follow-up tasks. Mathematics
skills distinguish proved results, conjectures, counterexamples, and unchecked
intuition; they ask agents to record assumptions and exact theorem references.
Every template identifies its version and permitted task capabilities. Prompts
do not grant GitHub permissions or override existing repository instructions.

The installer preserves existing `AGENTS.md` text and updates only its marked
section. Skill upgrades preserve human modifications: show a diff and propose
changes when a managed file has diverged, rather than overwriting it. Project
owners may customize skill prompts through reviewed changes. Private keys,
access tokens, and broker credentials never belong in instructions or hints.

## Standard work generated by the broker

The broker should do more than process explicit requests: it should enqueue
configured routine work when new repository work arrives. The mathematics
profile includes inspection for generalizations. The broker selects work using
trusted rules; an authorized agent performs the mathematical reasoning. The
privileged broker does not run a model or execute pushed project code.

For round one, reconcile pushes to the trusted default branch, merged PRs, and
verified task completion against a durable cursor. Default-branch pushes cover
work that bypasses the agent task loop, including maintainer commits. A scheduled
sweep catches missed notifications. An optional project rule may inspect a
verified open PR before integration, with results tied to its exact head SHA.
[GitHub workflow events](https://docs.github.com/en/actions/reference/workflows-and-actions/events-that-trigger-workflows)

Rules in protected `standard-work.json` define a rule ID and version, enabled
state, event eligibility, mathematics path filters, prompt template, required
skill, priority, evidence policy, and task limits. A mathematics profile proposes
filters for that repository's proof sources and mathematical documents; it does
not treat every Markdown edit as new mathematics. Configuration is reviewed
alongside the broker's other protected inputs.

For example, a merged PR adding a theorem creates an ordinary queued task:

> Inspect the mathematical changes in PR 42 at commit SHA for possible
> generalizations. Identify assumptions that can be weakened, broader structures
> or parameter ranges, reusable lemmas, and limitations or counterexamples.
> Commit a review recording what was checked and why each proposed extension is
> supported, conjectural, or ruled out. Create separate actionable follow-ups
> where useful. A reasoned finding that no useful generalization exists is valid.

The task records source repository, PR or commit range, exact SHA, originating
rule and configuration revision, skill version, and provenance. Its review
artifact links to theorem names or source locations, lists assumptions, and
records checks performed. Ordinary evidence policy still applies: a review task
needs a committed artifact and required passing GitHub checks. Schema checks
can verify that a report exists and is structured; they do not prove its
mathematical conclusions. Formalization or independent review can be separate
follow-ups when the project requires stronger evidence.

Other configurable standard tasks include proof-gap inspection, reusable-lemma
extraction, and updating mathematical documentation. Projects choose which rules
to enable. These are ordinary queue entries, visible and editable by authorized
humans, rather than invisible broker side effects.

## Avoiding duplicate and recursive work

A generated task gets a stable identity derived from the repository, rule ID and
version, and canonical source change. A PR merge and its push notification must
resolve to the same source; unassociated pushes use a reconciled commit range.
Commit generation receipts, cursor advancement, and new tasks atomically on the
state branch. Replayed events and broker retries cannot produce extra tasks.

Group relevant changes into one inspection per PR or bounded push batch. Ignore
state-branch commits and changes consisting only of hints, coordination files,
or generated review reports. By default, a standard review does not trigger
another standard review. Material new proofs produced by a follow-up may trigger
inspection under the rule's explicit depth and task-count limits. When a limit
is reached, show a deferred-work notice rather than dropping the source silently.

A dismissed or cancelled automatic task retains its generation receipt so a
sweep does not recreate it. Changing a rule version does not automatically
backfill history; an explicit bounded backfill request is required. Pausing a
rule stops future generation without erasing tasks already created.

## Viewer and queue editing

The static Tailwind viewer is a queue editor as well as an inspector. It shows
large project cards across selected repositories and, within a project, tasks,
subtasks, dependency graphs, leases, provenance, conversations, and proof links.
It must expose these ordinary human actions:

- Add tasks and subtasks with concrete acceptance criteria and dependencies.
- Edit titles, descriptions, acceptance criteria, and dependency relationships.
- Set priorities and reorder the ready-work preference list.
- Inspect, pause, or dismiss standard work and follow its source change.
- See pending requests, accepted changes, validation errors, and conflicts.

The browser submits authenticated human requests to the repository's Issue inbox;
it never writes the state branch directly or receives the broker credential.
The broker verifies the actual GitHub author and project permissions. Protect
unsigned human requests against edits by another actor, as specified in the
[identity design](design.md). Agents continue to use signed requests.

Every task has a revision, and queue ordering has a revision. Edits include the
expected revision. On a conflict, the viewer preserves the unsaved draft and
shows the newer state for reconciliation; it does not silently overwrite another
person's change. A request remains visibly pending until its receipt arrives.
Reordering is atomic and does not preempt active claims.

Acceptance criteria and dependencies of an active task cannot change silently.
A maintainer can explicitly release and invalidate its claim before applying a
material edit. Completed evidence remains linked to the task revision it proved;
changing the objective creates a new task rather than rewriting that history.
Cancelling work invalidates its lease and leaves dependents blocked until an
explicit graph edit resolves them. All operations preserve an audit record.

## Acceptance of the deliverables

A round-one release should demonstrate a fresh repository installation, a second
installation without duplicate files or tasks, preservation of existing agent
instructions, and an upgrade with customized skills. `doctor` must verify the
actual permission boundary, not merely configuration files.

End-to-end verification should cover competing claims, revoked agents, replayed
requests, stale edits, cycles, proof failure, and retry after a broker crash. A
mathematics push must produce one inspection task despite duplicate triggers;
a review-only follow-up must not recursively create another review. The viewer
must add, edit, and prioritize through accepted receipts while preserving a
conflicting user's draft. Missing GitHub events must be recoverable by sweeping.

Use pytest for meaningful protocol and integration tests, Ruff with standard
isort and Black-compatible formatting, and ty for types. GitHub Actions runs
those checks and builds/deploys the viewer. Real permissions and workflow triggers
also require a disposable GitHub repository smoke test before claiming the setup
is ready. The current local implementation remains a draft.
